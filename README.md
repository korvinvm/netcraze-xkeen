# Netcraze Ultra (NC-1812) — обход блокировок и гостевая сеть

Собрано 2026-11-03. Всё, что нужно, чтобы понять, восстановить или переделать конфигурацию.

---

## 1. Железо и прошивка

- **Модель:** Netcraze Ultra, `NC-1812` (линейка Keenetic, NDMS, не OpenWrt).
- **Прошивка:** `5.01.C.8.0-2` (title 5.1.8), arch `aarch64`, sandbox stable.
- **Роутер:** `192.168.2.1`, логин `admin`, пароль см. `SECRETS.md`.
- **WAN:** `192.168.1.65` в сети Alina (кабель в LAN-порт роутера `alina5g`), шлюз `192.168.1.1`.
- **USB-флешка:** 3.4 ГБ, ext4, смонтирована в `/tmp/mnt/<uuid>`, Entware в `/opt`.
- **SSH:** порт 22, dropbear, только старые алгоритмы (см. `router/router_ssh.py`).
- **Веб-панель:** `http://192.168.2.1` (NDMS Web Panel), API `/rci/` — авторизация по challenge,
  с новыми прошивками напрямую не завелась, работаем через SSH.

## 3. Подписка

- Источник: `https://sub.conn-liberty.net/connection/subs/<uuid>` (адрес хранится вне репозитория, в `/opt/etc/xray/sub.url`).
- Формат ответа: **JSON-массив из 40 готовых конфигов Xray**, не base64-список.
- Берётся первый элемент (`.[0]`): 13 серверов VLESS+REALITY, правила: `block` для UDP/443 (QUIC),
  `direct` для 66 российских доменов, остальное — в прокси.
- Выходные адреса серверов — CDN77/DataCamp (Швеция, Нидерланды, Германия, Польша), все помечены
  как `hosting=true, proxy=true`. Это влияет на Google: Gemini может выдавать «Что-то пошло не так».

### Файлы конфигурации Xray

Xray читает **каталог** `/opt/etc/xray/configs/` (переменная `XRAY_LOCATION_CONFDIR`), а не
`config.json`. Важно: правки в `config.json` игнорируются.

- `01_log.json` — журнал
- `02_transport.json` — пустой
- `03_inbounds.json` — входы (см. ниже)
- `04_outbounds.json` — серверы из подписки (генерируется)
- `05_routing.json` — правила (генерируется)
- `06_policy.json` — таймауты
- `07_dns.json` — DoH 8.8.8.8/8.8.4.4

### Входящие подключения (inbounds)

| Тег | Протокол | Порт | Для чего |
|---|---|---|---|
| `redirect` | dokodemo-door (followRedirect) | 61219 | основная сеть, 80/443 |
| `guest` | socks | 127.0.0.1:1082 | проверки и внешние клиенты |
| `guest-all` | dokodemo-door | 61220 | гостевая сеть, весь TCP |
| `dns-in` | dokodemo-door | 5354 | DNS-запросы обеих сетей |

Порт **5353 занят mDNS** — поэтому DNS-вход на 5354.

## 4. Сети

### Основная — `Netcraze-6020`
- 2.4 + 5 ГГц, WPA2/WPA3, пароль в `SECRETS.md`, band steering включён.
- Подсеть `192.168.2.0/24`, DHCP-пул `.33–.152`.
- Трафик: **всё, что на 80/443**, перехватывается и уходит в Xray (порт 61219) → правила:
  российские домены напрямую, остальное через сервер из подписки.
- **DNS тоже через туннель** (порт 53 → 5354 → DoH через прокси), утечки к провайдеру нет.

### Гостевая — `Netcraze-Guest`
- 2.4 ГГц (интерфейс `WifiMaster0/AccessPoint1`), **WPA2**, пароль `guest12345`.
- Подсеть `10.1.30.0/24`, шлюз `10.1.30.1` (интерфейс `Bridge1` «Guest network»), DHCP-пул `.33–.152`.
- **Строгий режим:** весь TCP → Xray 61220 → только прокси, без исключений для российских сайтов.
  DNS → 5354 через туннель. **IPv6 заблокирован** (иначе трафик уходил бы мимо).
- Сегмент изолирован от LAN: из гостевой `192.168.2.1` недоступен, только `10.1.30.1`.

## 5. Правила iptables (hook `zz-guest-xray.sh`)

Скрипт лежит в `/opt/etc/ndm/netfilter.d/` и **переустанавливает правила при каждой пересборке
netfilter** средствами NDMS. Ручные правки iptables не переживут перезагрузку.

- Цепочка `guestxray`: DNS (53) → REDIRECT 5354, приватные адреса → RETURN, весь TCP → 61220.
  Вставляется в PREROUTING для `-s 10.1.30.0/24` и для метки `0xffffaac/0xfffffff`.
- Цепочка `lanxray`: DNS → 5354, 80/443 → **REDIRECT 61219**, остальное RETURN.
  Вставляется в PREROUTING для `-s 192.168.2.0/24`.
- `guestxray6`: DROP для IPv6 гостей.

**Грабли:** сначала здесь стоял переход в цепочку `xkeen` (родную для XKeen). Она срабатывает только
по метке политики, а у устройств метка `0` — перехват молча не работал, и трафик шёл напрямую.
Поэтому сейчас — прямой REDIRECT в 61219.

## 6. Сторож и отказоустойчивость

`/opt/etc/init.d/S99xrayguard` — свой демон, потому что **cron на этой прошивке задания не выполняет**
(проверены и spool `/opt/var/spool/cron/crontabs/root`, и `/opt/etc/crontab`).

- **Раз в 5 минут**: `health.sh` — пять попыток `curl --socks5-hostname 127.0.0.1:1082 https://api.ipify.org`;
  если все провалились и с прошлой смены сервера прошло больше 15 минут → `sub-sync.sh`.
- **Раз в 30 минут** (6 циклов): полное обновление подписки.
- Блокировки `health.lock` / `sync.lock` не дают прогонам наложиться.
- `sub-sync.sh`: скачивает подписку **двумя путями** — сначала напрямую, если не вышло, то
  **через уже поднятый туннель** (`--socks5-hostname 127.0.0.1:1082`). Это закрывает случай
  «прямой путь к подписке заблокирован, а сервер ещё жив».
- Скачанное проверяется на формат конфига Xray, и только потом подменяет рабочие файлы;
  предыдущая версия остаётся в `sub.last` и в `*.prev` до успешной проверки.
- Серверы сначала щупаются **TCP-коннектом** (`nc -w 3`) — мёртвые адреса не тратят
  перезапуски xray. Далее конфиг проверяется `xray run -test -confdir`, поднимается,
  и проверяется внешний IP через SOCKS.
- Если не поднялся ни один сервер — откат на прежний конфиг и **повтор через 10 минут**
  (фоновый `sleep`), а не ожидание следующего цикла.
- Журнал: `/opt/var/log/xray-sub.log`.

Команды:

```sh
/opt/etc/init.d/S99xrayguard status|start|stop|restart
/opt/etc/xray/health.sh          # одна проверка
/opt/etc/xray/sub-sync.sh        # обновить подписку и перебрать серверы
```

Проверено на живом отказе: Xray погашен → сторож поднял его на другом сервере.

## 8. Доступ к роутеру с ноутбука (обход перехвата `happ`)

`happ` (WinDivert/туннель на ноутбуке) забирает маршруты и ломает доступ к `192.168.2.0/24`.
Решение — **привязка исходящих соединений к адресу ноутбука в сети роутера**:

- `router/fwd.py` — TCP-форвардер `0.0.0.0:2222 → 192.168.2.1:22` с `bind` на `192.168.2.145`;
- `router/router_ssh.py`, `router_run.py`, `router_put.py`, `router_shell.py` — SSH к роутеру
  через `host.docker.internal:2222` (запускаются внутри контейнера `astrology-bot`, там есть paramiko).
- Запуск форвардера: `python fwd.py 2222 192.168.2.1 22 192.168.2.145`.

Проверка, что дело в маршрутах: `ping -S 192.168.2.145 192.168.2.1` — 0% потерь; без привязки — 100%.

### `happ` и «интернет пропал без него»
При закрытии `happ` его адаптер `happ-default-tun` остаётся в таблице маршрутов с метрикой 0 —
Windows продолжает слать трафик в мёртвый туннель. Лечится `windows-tools/kill-happ.ps1`:
гасит службу `HappService`, удаляет маршрут, отключает адаптер.

## 9. Проверка «всё ли работает»

С роутера:

```sh
/opt/bin/curl -s --socks5-hostname 127.0.0.1:1082 https://api.ipify.org   # иностранный IP
/opt/bin/curl -s https://api.ipify.org                                    # провайдерский IP
netstat -ltn | grep -E ':1082|:61219|:61220'
iptables -t nat -L PREROUTING -n | grep -E 'lanxray|guestxray'
```

С ноутбука:

```powershell
curl -s --interface 192.168.2.145 https://api.ipify.org   # должен быть иностранный
curl -s -o NUL -w "%{http_code}" https://www.youtube.com  # 200
nslookup google.com                                        # резолвится
```

## 10. Что осталось / известно

- `HappService` стоит в автозапуске — при перезагрузке снова перехватит маршруты. Решение
  пользователя: отключить автозапуск или оставить.
- Выходные адреса всех серверов подписки — датацентр (CDN77/DataCamp/GTHost), у всех флаг
  `proxy=true`. Из-за этого Google может показывать «подозрительный трафик» и Gemini иногда
  отдаёт `Something went wrong (1)`.
- Порт 5353 (mDNS) занят системой — не переносить туда DNS.
- `xray run -test` проверяет конфиг, но не запускает его: ошибки вроде занятого порта видны только
  при старте.

## 11. Утечки, найденные позже (и закрытые)

Google с телефона видел российский адрес, хотя ноут ходил через туннель. Причины оказались две,
обе закрыты в `zz-guest-xray.sh`:

1. **QUIC (UDP 443).** Перехват ловил только TCP 80/443, а Chrome и телефоны предпочитают QUIC
   поверх UDP — трафик шёл мимо туннеля. Теперь UDP 443 из обеих сетей роняется (цепочка
   `lanquic`), клиент сам падает на TCP, который уже проксируется.
2. **IPv6.** У роутера есть глобальный IPv6, туннель — только IPv4. Теперь IPv6 из `Bridge0` и
   `Bridge1` не выпускается наружу (цепочка `lan6` в ip6tables).

Проверка, что поймали: `iptables -L FORWARD -n -v | grep lanquic` — счётчики должны расти.

**Важно:** правила применяются только к **новым** соединениям. После правки надо переподключить
устройство к Wi-Fi, иначе старые сессии продолжают идти по-старому.

## 12. Стабильность внешнего IP (после жалоб на Gemini)

Google сравнивает IP начала и текущий адрес сессии и при расхождении выдаёт
«Мы зарегистрировали подозрительный трафик». Расхождение возникало из-за ротации серверов.

Сделано:

- `sub-sync.sh` теперь **пробует текущий сервер первым** (`current_tag`), и если он жив — ничего не
  меняет. В логе строка «текущий сервер пробуем первым».
- `health.sh`: 5 попыток вместо 3, и **пауза 15 минут** между сменами (`/opt/var/xray-sub/last_rotate`).
- Обе сети (основная и гостевая) используют один и тот же outbound-тег — при переключении между
  сетями IP не меняется.

Проверка стабильности: `/opt/etc/xray/sub-sync.sh` дважды подряд — внешний IP должен совпасть.
Скрипт `router/restore.sh` возвращает активный сервер из `current_tag` после экспериментов.

**Если Gemini всё равно ругается:** сначала полностью закрыть Chrome (он держит сломанное
HTTP/2-соединение), затем инкогнито. Если и там ошибка — смотреть F12 → Network, какой хост
красный. Сами адреса серверов подписки помечены как прокси, и Google это не любит — это уже
не утечка, а репутация выходного IP.

## 13. DNS не падает вместе с Xray (правки 14.11.2026)

Симптом: «интернет вроде есть, а страницы не открываются». Причина — правила `lanxray` /
`guestxray` отправляют DNS клиентов на Xray `:5354`; пока Xray перезапускается, слушателя нет,
имена не резолвятся, хотя TCP по IP работает. Перезапуски шли пачками: `sub-sync` дёргал Xray
даже когда текущий сервер был жив, `keeper` при первой неудачной пробе менял сервер, и каждое
переключение снова роняло DNS.

Что сделано:

- **sub-sync**: если туннель отвечает две пробы подряд — подписка только сохраняется, конфиг и
  Xray не трогаются (`FORCE_SYNC=1` — принудительно). В логе: «Xray не перезапускаю».
- **sub-sync**: перед перезапуском Xray сервер проверяется TCP-коннектом — мёртвый адрес больше
  не стоит клиентам DNS.
- **keeper**: переключение только после 3 неудачных проб подряд, пауза 90 с между сменами,
  до 15 с ожидания после перезапуска (раньше 2 с — живой сервер объявлялся мёртвым).
- **keeper**: пишет `current_tag` (раньше только `current`, и sub-sync не знал активный сервер).
- **dns-watch**: тик 5 с вместо 15; перезапуск Xray после 10 с без слушателя.
- **`/opt/etc/xray/dns-failopen.sh on|off|status`** — если Xray не поднялся с первого
  перезапуска, DNS клиентов уходит к резолверу роутера (правило `RETURN` перед `REDIRECT`),
  при возврате `:5354` снимается само. Пока включён — DNS идёт мимо туннеля: осознанный размен.
- убран cron `tick.sh` (писал строку в минуту в `mark.log`), логи почищены.

Замер: `kill -9` Xray → слушатель и DNS вернулись за 6 с, сервер и внешний IP не менялись.

```sh
/opt/etc/xray/dns-failopen.sh status
tail -5 /opt/var/log/dns-watch.log
grep -c 'Xray не перезапускаю' /opt/var/log/xray-sub.log
```
